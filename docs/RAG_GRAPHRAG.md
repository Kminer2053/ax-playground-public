# 사규 RAG — 하이브리드 검색 종합 가이드 (키워드 · 의미 · 그래프)

AI 지식검색(`/panel/knowledge`)이 임직원 질문에 **사규 근거를 찾아 답하는** 방식의 전부를 담은 문서다. 처음 보는 사람도 구조를 이해하고, 운영자가 직접 유지·관리할 수 있도록 쓴다.

**한 문장 요약**: 질문을 **세 가지 방법(키워드·의미·그래프)으로 동시에 검색**해 관련 사규를 모으고, **내부망 로컬 LLM**이 그 근거만으로 답을 쓴다. 외부 API는 일절 쓰지 않으며 모든 호출은 가드레일을 거친다.

> 함께 보기 — 데이터 적재(원문 정제·청킹): [`사규_시드_실행_가이드.md`](사규_시드_실행_가이드.md) · 동작 도식: [`ARCHITECTURE.md`](ARCHITECTURE.md) · **그래프 관계 스키마·증분 유지 표준(로컬 단독 관리의 핵심)**: [`GRAPH_SCHEMA.md`](GRAPH_SCHEMA.md) · 평가셋: `data/benchmark/queries.json`.

## 1. 한눈에

```
질의 ──┬─ 키워드($text + RegExp)  ─────────┐
       ├─ 의미(bge-m3 임베딩 코사인)  ──────┤→ 시드 문서 ─→ 그래프 확장 ─→ 컨텍스트 ─→ 내부 LLM ─→ 답변
       └─ (시드의 질의관련 청크) ───────────┘   (rag_graph_edges: 참조·위계)   (출처 표식·관계 근거문장)
```

세 신호가 서로의 약점을 메운다:
- **키워드** — 정확 일치(법령용어·조문번호). 빠르지만 표현이 다르면 놓침.
- **의미** — 표현이 달라도 회수("갑질"→직장 내 괴롭힘, "배상"→직원변상). bge-m3 임베딩.
- **그래프** — 시드 문서가 **참조하는 다른 규정**을 끌어옴("계약심의회"→직제 규정). 규정 간 관계까지.

**효과(A/B, 20개 라벨 질의 · `eval-graphrag.ts`)**: 정답문서 회수율 **전체 55→90%**, **의미형 질의 20→80%**, 회귀 0건.

## 2. 간편검색 vs 심층검색 — 무엇이 다른가

같은 사규를 검색하지만 **두 모드**가 있다. 사용자가 토글로 고른다.

| | **간편검색**(fast) | **심층검색**(deep) |
|---|---|---|
| 목적 | 빠른 직답 | 꼼꼼한 근거·관계 설명 |
| 의도 파악 | 없음(질문 그대로 검색) | **LLM이 의도 요약 + 키워드 확장** 후 검색 → 더 넓게 회수 |
| 회수 문서 수 | 5건 | 8건 |
| 답변 형식 | 자유 직답 | **4섹션 구조**(`## 요약 / ## 근거 / ## 적용 순서·유의 / ## 한계·추가 확인`) |
| 관계 설명 | 안 함 | **그래프 관계 근거문장 표출**(아래 §5) — "「A」는 「B」에 근거함" 식으로 규정 간 연결을 논리적으로 설명 |
| 토큰·시간 | 적음·빠름 | 많음·느림(의도파악 + 4섹션 생성으로 LLM 2회 호출) |
| 쓰임새 | "연차 며칠?" 같은 단순 사실 | "이해충돌 의무가 취업규칙과 어떻게 연결돼?" 같은 복합·관계·근거 질의 |

**왜 관계 설명은 심층 전용인가**: 측정 결과, 관계 합성은 *꼼꼼한 심층 답변*에는 품질을 높이지만(정답인용 72→80) *단순 간편 답변*에는 군더더기가 돼 오히려 품질을 떨어뜨렸다. 그래서 **심층에만** 켠다(코드: `buildContextText(..., deep)` 게이팅).

구현: `src/app/api/knowledge/assistant/route.ts`. 모드는 요청 `{mode:"fast"|"deep"}`.

## 4. 검색 파이프라인

진입점: `route.ts`. 단계:

1. **(심층) 의도·키워드 확장** — 내부 LLM으로 질의 의도 요약 + 동의어·관련 제도·법령명 추출. **단, 확장은 *회수(recall)* 전용**이다: 심층도 **원질문**으로 1차 회수해 랭킹 기준을 잡고, 확장질의 회수분은 *뒤에 덧붙여* recall만 보강한다. 확장이 보편어로 드리프트해도 원질문 의도가 순위를 지배한다(보편어 편향 방지의 핵심).
2. **키워드 회수** — `retrieveRagRegulationsForQa`: MongoDB `$text` + RegExp로 후보 회수.
3. **재랭킹 — 어휘 + 3신호** (`rerankHits`) — 어휘매칭(위치·용어비율·구절) 위에 다음 3신호를 합산해 **보편어 편향을 교정**한다:
   - **의미(벡터)**: bge-m3 코사인 주제 적합도 — '전문점 계약'과 '광고 계약'을 구분. 항상 **원질문** 기준(임베딩은 동의어를 알아서 처리 → 확장 불필요·금물).
   - **그래프-정합성(coherence)**: 후보들이 같은 도메인 군집으로 `doc→doc` 참조 연결됐는지(`graphCoherence`). 연결문서 **가산만**(그래프 sparse → 감산은 관련문서까지 떨굼).
   - **제목 매칭(특정성)**: 질의어가 문서 *제목*에 많이 들수록 가산 — 「전문점 운영 계약서」(전문점+계약)가 generic 「계약업무 처리지침」(계약)을 앞선다. 그 뒤 위계 정렬.
4. **의미 시드** — `vectorSearchSeeds`(원질문): bge-m3 임베딩 → 인메모리 코사인 → 문서 단위 묶음. **키워드에 없는 문서만** 추가(`vecHit`). 위 3-①의 벡터 점수와 같은 회수를 재사용.
5. **그래프 확장** — `expandViaGraph`: (키워드+의미) 시드의 **질의 관련 청크**에서 출발하는 `chunk→doc` 참조 엣지 회수. 관련 규정 추가(`viaGraph{from,rel,reason}`).
6. **컨텍스트 조립 + 생성** — 위계 순으로 묶고 출처·**역할 라벨**을 달아 내부 LLM에 전달. 심층은 `【규정 간 관계】` 블록(그래프 근거문장)도 첨부.
   **문서 안 '조문' 선택**(2026-07-03 개선, §5-4): 인용표시와 동일한 **이진 스코어러**로 통일(출현빈도 합산의 별표 길이편향 제거) + **벡터 조문힌트**(문서별 상위 조문 코사인, top3→키워드 관련도 재정렬 2슬롯 보장) + **조문당 예산 캡·밀도순 히트창**(한 블록의 예산 독식·꼬리 신설항 유실 방지).
   이 파이프라인은 `src/lib/regulations-search.ts` **공용 모듈**로 추출되어 **문서작성 사이드챗**(`/api/ai/chat`)도 동일 품질로 공유한다.

> **그레이스풀 디그레이드**: 임베딩 서버(Ollama)가 꺼져 있으면 의미 시드는 무시되고 키워드+그래프만, 그래프 미적재 시 키워드만 동작.

**런타임 채널 스위치**: `PlaygroundConfig`(관리자)에서 `ragVectorEnabled`·`ragGraphEnabled`로 **재시작 없이** on·off. env `VECTOR_SEARCH=0`·`GRAPH_EXPANSION=0`·`BM25_SEARCH=1`(BM25 opt-in)은 하드 토글.

## 5. 품질향상 설계 — **측정 기반**(무엇이 효과 있었나)

> 핵심 원칙: **단발 질문으로 단정하지 않는다.** `data/benchmark/queries.json`(유형별: 직접·의미·참조·범위밖 — 동봉본은 샘플 사규 기준 20문항 더미, 기관 데이터 적재 후 자체 문항으로 교체)으로 간편·심층 모두 A/B 측정하고, 지표뿐 아니라 **실제 답변을 읽어** 판단한다. 도구: `benchmark.ts`(풀) · `quick-eval.ts`+`build-quick-compare.py`(약식 10문항 좌우 HTML).

**채택된 개선**
1. **역할구분 프롬프트(v1b)** — 근거문서마다 `[역할: 규범·원칙 / 절차·방법 / 예시·근거]` 태그를 달고, 규정=원칙·방향, 편람/매뉴얼=구체 방법, 계약서=예시로 쓰도록 지시. → 간편 정답인용 **70→77%**, 의미형 **62→74%**. 베이스라인이 일부 질문에 "인사말로 때우던" 실패(punt)를 제거.
2. **그래프 관계배선(심층 전용)** — 그래프 엣지의 관계유형(rt)·근거문장을 `【규정 간 관계】`로 생성 컨텍스트에 노출 + "근거·준용·위임 연결을 논리적으로 설명하라" 지시. → 심층 정답인용 **72→80%**(전 카테고리↑).
3. **재랭킹 3신호 — 의미·그래프정합성·제목(특정성)** — 키워드($text)는 보편어("계약")에 끌려 특정어("전문점")를 묻고, 어휘만 겹친 **타 도메인 오답**(광고 영업파트너사 계약서)을 상위로 올리는 약점이 있었다. 재랭킹에 ① 의미(벡터, 원질문) ② 그래프 군집 연결도(`graphCoherence`) ③ 제목 매칭을 더해 교정 + **확장은 recall 전용·랭킹은 원질문**(§4-1). → recall@5 **69.6→77.2%**(의미형 **52→66%**, 직접 유지, 참조 100%·회귀 0). "전문점 계약" 질의가 광고 규정을 떨치고 전문점 운영 규정 중심 답변으로 전환. 측정도구: `diag-ab-recall.ts`(유형별 recall A/B), `diag-deep-refs.ts`(심층 회수 복제).
4. **컨텍스트 '조문 선택' 개선(2026-07-03)** — 증상: 정답 *문서*는 찾는데 답변이 일반론·"자료에 없음"으로 회피(예: 개정된 계약보증금율 질의). 실측 원인 3가지 — ⓐ 컨텍스트용 조문선택이 **출현빈도 합산**이라 1만자급 별표(일반조건)가 짧은 정답 조문을 밀어냄(길이편향) ⓑ 1위 블록이 예산을 독식하고 꼬리를 잘라 **나머지 조문·신설 항(⑦⑧) 통째 유실** ⓒ 벡터가 계산한 **조문별 코사인**(정답 조문 1위/4,317)이 버려지고 문서 선택에만 쓰임. 해법: 인용표시와 선택기 통일(이진 스코어러) + 벡터 조문힌트 2슬롯(top3→키워드 재정렬 — 코사인 박빙 오선택 방지) + 조문당 캡·밀도순 히트창(토큰별 히트 배분 — 희소 정답어 수집 보장). → **개정조문 4문항 0/4→3.5/4** · 랜덤 20 A/B(옛/새 조립, 동일 gemma): fast **9승2패9무** · deep **8승2패10무**(정답규정 인용율 85→90%) · 문서레벨 recall@5 **회귀 0**(75%=75%). 부산물: 검증 과정에서 "gemma가 근거를 못 읽는다"는 초기 가설이 틀렸고 **근거가 컨텍스트에 아예 없었다**는 것을 실측으로 확인 — citations(표시)와 컨텍스트(입력)가 서로 다른 선택기를 쓰던 불일치도 함께 해소.

**측정으로 *걸러낸* 것(헛발질 방지)** — 다음은 이론상 그럴듯했으나 측정에서 효과가 없어 도입하지 않았다:
- **BM25(한국어 lexical)**: 103문서 코퍼스는 키워드+의미가 이미 회수를 포화시켜 **중립**. 코드는 `regulations-bm25.ts`에 보존(코퍼스가 수천 건으로 커지면 `BM25_SEARCH=1`로 재평가).
- **IDF로 특정성 가중**: "전문점>계약" 특정성을 char-bigram IDF로 주려 했으나, bigram-IDF가 활용형 어미("안내해야할")를 명사("전문점")보다 높게 매겨 **역효과**. 특정성은 IDF가 아니라 **제목 매칭 + 의미(벡터)**로 해결(위 §5-3).
- **그래프의 *검색* 기여**: 벡터와 역할이 겹쳐 **회수 기여 0**. 그래프의 진짜 가치는 *검색*이 아니라 *관계형 생성*(위 관계배선)에 있다.
- **naive few-shot으로 로컬모델 향상**: 작은 모델(gemma-4-e2b)은 예시에 과민해 오히려 분류가 나빠짐 → 롤백.

5. **표 기준표 행 명제화 — tableGloss(2026-07-03)** — 증상: 최빈 업무질의 4유형(금액→전결권자·사건→징계양정·연차기준·부서→평가기준)은 답이 **별표/별지 기준표**에 있는데, 평탄화된 표(2단 병합 헤더가 데이터행으로 밀림·rowspan 붕괴)에선 문서를 찾아도 **정답 행이 컨텍스트에 못 실림**(표형 골드셋 55%). 해법 3단: ⓐ **표 성격 4분류**(`regulations-table-classify.ts`: A기준표/B서식표/C본문표/D연혁 + 사람검수 확정 `data/table-overrides.json` 117건 — 재태깅에도 영속) ⓑ **A 기준표 행 명제화**(`regulations-table-gloss.ts`: 전결●표·양정표·매핑표 3파서 → "업무 → 직급 전결 (금액: 2천만원)" 행 문장, `articles[].tableGloss` **별도 필드** — 원문·srcHash·diff 불변, 롤백=$unset; 임베딩은 명제 선행 합성) ⓒ **검색 배선**: 조문 스코어 gloss 합성+기준조회 가산, 발췌에 질의 히트 명제 부착 + **glossReserve**(벡터 힌트가 예산 선점해 대형 별표가 통째 탈락하던 역전 방지 — 원칙 조문과 표 해석 공존), 금액 **구간 산술**(500만원∈"일천만원 이하", 경계값은 양쪽 행 제시), 어휘 렉시콘(결재↔전결·구매↔구입·빌리다↔금전대차), 아라비아→한글 금액 토큰("2000만원"→"이천만원"). 재적재 시 `regulations-table-retag.ts`가 태깅·명제·재임베딩 **자동 재생성**(관리자 적재·reg:ingest 공통). → 표형 골드셋(122문항, `eval-table-gold.ts`) 정답행 탑재 **55→97%**, 실답변 A/B(랜덤50×빠른/심층, `eval-ab-answers.ts`) 정답발화 **빠른 55→79%·심층 62→90%·악화 0**, 기존 recall@5 **76.1% 유지**. 골드셋 원칙: evidence는 **원문 실재 조각만**(명제 롤백 시에도 공정 측정) + 일부러 남긴 미해결 앵커(비핵심 문서)로 다음 개선 감지력 유지.

**교훈**: "측정·읽기 검증"이 설계의 중심. 자세한 실험 로그는 [`GRAPH_SCHEMA.md`](GRAPH_SCHEMA.md) §8.

## 6. 지식그래프

**노드** = 문서(103) + 청크 + 외부법령(가상). **엣지**(`rag_graph_edges`):

| kind | 의미 | 스키마 |
|------|------|--------|
| `hier` | 위계(직상위) | `{sdoc, tdoc}`(자식→부모) |
| `ref` | 내부 참조(검증됨) | `{sdoc, sci, sname, rt, tt:chunk\|doc, tdoc, tci?, tname?, reason, rtConf}` |
| `law` | 외부법령 의존 | `{sdoc, sci, sname, tt:law, tgt, lawName?, rt?, reason?}` |

- **관계유형(rt) 13종**: 근거·준용적용·서식첨부·절차·위임·정의·예외 + (확장) 상충·우선·개정·시행·법령위임근거·제재·벌칙·선후·전제·특례. 단순 "참조"가 아니라 **성격까지 라벨링**하고, `reason`(근거문장)·`rtConf`(신뢰도 상/중/하)를 함께 저장한다. 정의·트리거·예시는 [`GRAPH_SCHEMA.md`](GRAPH_SCHEMA.md).
- **빌드 = 2단계**: ① 규칙(정규식)으로 후보 추출(LLM 불필요) → ② LLM 검증(진위 + 관계유형). 내부조문 후보의 84%가 시행령·법 오인이라 **LLM 검증 필수**.
  - **전체(고품질) 빌드**: 클라우드 Opus 멀티에이전트로 절-grounding 재타이핑(2,785 엣지 전수, 절 본문에만 근거·불명확 시 보류=할루시네이션 0). law는 절에서 외부법령 식별 + WebFetch(국가법령정보센터) 스팟검증. 결과를 스냅샷에 박제해 폐쇄망에 동봉.
  - **증분(운영) 빌드**: 폐쇄망 = 내부 gemma. 아래 §8.
- **관계 표출(심층)**: 교차규정(tt:doc)은 `expandViaGraph`로 **문서까지 확장**하고, **문서내 조문간(tt:chunk)·외부법령(law) 관계는 `seedRelations`로 `【규정 간 관계】`에 진술만 추가**(새 문서를 끌어오지 않고 관계만). → 검증에서 누락되던 within-doc 관계(예: 인사규정 당연면직 제46조 ↔ 직권면직 제47조)가 답변에 함께 표출됨. (개별 조문 청크검색 등 더 깊은 활용은 향후 여지)

## 8. 로컬모델 사후관리 — 폐쇄망에서 품질 유지하기

폐쇄망엔 Opus가 없다. 규정이 하나씩 늘 때 **내부 gemma로 그래프·임베딩을 유지**해야 한다. 핵심은 *"로컬모델에게 추론을 시키지 말 것"* — 지능을 **규칙·예시·사람**에 둔다.

**증분 적재**(관리자 사규 적재 탭 또는 CLI `npm run reg:ingest`, 그 문서만): `updateGraphForDoc(title, directParent?)`
1. 해당 문서 청크 재색인 — 단 **무변경 조문은 재계산 skip**: 조문 해시(`srcHash`/`h`)가 같으면 **기존 임베딩·엣지를 인덱스만 재매핑해 재사용**(LLM·임베딩 비용 = 변경 조문만). 실측(계약업무 226조문 재적재): 벡터 204/204·엣지 567 전량 재사용, 신규 도출 0.
2. 변경·추가 조문만 참조 후보 추출(규칙) → **로컬 LLM 검증**. gemma-2B가 출력형식을 자주 어겨 **조용히 폴백**(내부조문 전멸·rt 전부 "기타")하던 문제를 발견 → **강건 파싱**(대괄호·원문자·파이프 수용) + `llmFallback` 카운트를 적재 UI에 경고 표출.
3. '엣지 0개' 조문은 해시를 `kind:"arthash"` 메타에 박제 — 재적재 때마다 gemma가 재도출해 그래프가 점증 드리프트하던 문제 방지.
4. `rag_graph_edges` 갱신. **신규는 직상위규정 입력 필수**(없으면 외부법령 처리). 시행일(최신 부칙)·연번(기존 승계)은 자동.
- 삭제/개명: `removeGraphForDoc`. API: `POST`/`PATCH`/`DELETE /api/admin/regulations`(`maxDuration 300`).
- ⚠ **그래프 품질 기준선은 Opus 박제 스냅샷**: 재도출은 gemma 품질(관계유형 뭉개짐·누락 관찰)이므로, srcHash 재사용이 Opus 엣지를 보존하는 안전판이다. 대규모 재도출분은 §8-4 Opus 재감사로 회복.

**관계유형 품질 유지(검증된 현실 레시피 — 측정 결과)**: 로컬 단독으로 Opus급은 비현실적이다. 대신:
1. **고정밀 규칙**(`regulations-rel-classify.ts`) — `…에도 불구하고`→상충·우선, `위반→제재`→제재·벌칙, 명시적 `준용/위임` 등 **확실한 트리거만 자동 채택**(conf 상).
2. **gemma + 예시은행**(`data/graph/fewshot-rel.json`) — 모호한 다수는 Opus가 만든 few-shot 예시로 정박해 판정. ⚠ 단 **균형 잡힌 소량 예시**만(편중되면 소형모델이 과일반화 → 역효과 확인됨).
3. **저신뢰는 사람 검토** — conf 중·하는 관리자 검토.
4. **주기적 Opus 재감사** — 누적분을 외부망 반출 또는 클라우드 접근 시점에 Opus로 일괄 재검토 → 스냅샷 재배포.
→ 기대 품질: 규칙+gemma+검토로 **약 60~74%**, gold는 Opus 재감사로 유지. (표준·도구·실측: [`GRAPH_SCHEMA.md`](GRAPH_SCHEMA.md))

**임베딩 유지**: 모델·차원 변경 또는 전면 재청킹 시 `build-embeddings.ts` 재실행.

**품질 회귀 테스트**: 검색·프롬프트·그래프를 바꾸면 반드시 `data/benchmark`로 A/B(약식 10문항 → 최종 100문항). 지표만 보지 말고 **답변을 읽어** 확인.

## 11. 빌드 vs 재빌드 — 주의

- **청크 인덱스 의존성**: 그래프(`sci`)·벡터(`ci`)는 청크 배열 인덱스가 키. 단건 증분은 정합 유지되나 **전면 재청킹은 인덱스가 어긋나** 그래프·임베딩 재빌드 필요.
- **질의 임베딩은 매번 자동**(Ollama 필요). **청크 임베딩·그래프는 적재 버전마다 1회**(DB 저장, 재시작에도 유지).

## 12. 배포(시드) · 기존 서버 업데이트

`rag_graph_edges`·`rag_vectors`는 시드 덤프(`data/mongo-snapshot` — 공개 리포 미동봉, 기관 데이터로 자체 생성)로 배포. 의미검색엔 Ollama에 bge-m3 필요.

**최초 설치 — 전체 복원**:
```bash
mongorestore --uri="mongodb://127.0.0.1:27017" --drop data/mongo-snapshot/dump-2026-07-03
```

**기존 운영 서버 갱신 — 사규(RAG) 3컬렉션만 교체**(⚠ 전체 `--drop`은 운영 설정·누적을 덮어씀). 세 컬렉션은 청크 인덱스로 묶여 있어 **반드시 함께** 교체한다. 절차는 ⓐ내보내기(개발/외부망) → ⓑ반입 → ⓒ반영(배포서버):

| 단계 | Linux/WSL2 | Windows(PowerShell) |
|---|---|---|
| ⓐ RAG만 덤프 | `bash scripts/export-rag-db.sh` → `data/mongo-snapshot/rag-update-YYYYMMDD/`(≈66MB) | `powershell -ExecutionPolicy Bypass -File scripts\export-rag-db.ps1` |
| ⓒ 배포서버 반영 | `MONGODB_URI=mongodb://127.0.0.1:27017 bash scripts/update-rag-db.sh [덤프경로]` | `powershell -ExecutionPolicy Bypass -File scripts\update-rag-db.ps1 [-Dump <경로>] [-Tools C:\mongodb-tools\bin]` |

- 두 스크립트 모두: 교체 전 **현재 3컬렉션 자동 백업**(`rag-backup-*`, 롤백 명령 안내) · 덤프 경로 미지정 시 최신 `rag-update-*`/`dump-*` 자동 선택 · 덤프 내부 DB명 자동 감지 · `MONGODB_DB`로 대상 DB 변경 가능.
- **폐쇄망 요건**: 외부 호출 없음(로컬 mongo만). 도구가 PATH에 없으면 sh는 `MONGO_TOOLS=<Database Tools bin>` env, ps1은 `-Tools <bin>` 지정(윈도우 오프라인 설치는 PATH 미등록이라 사실상 필수). `mongosh` 미포함 환경이면 카운트 검증만 생략(복원 성공과 무관, mongorestore 로그로 확인).
- **무중단 반영**: 앱 프로세스는 그대로 두고 ① `npm run sagyu:build`(좌측 목록 동기화) ② **관리자 → 설정 → [RAG 캐시 새로고침]**(`POST /api/admin/rag-cache` — 벡터·BM25 인메모리 캐시 초기화, **재시작 불필요**). 교체 중 수 초간 검색 결과가 일시 축소될 수 있으나 서비스는 중단되지 않는다. (버튼이 어려우면 재시작으로 동일 효과)
- **권장 파이프라인(개발 맥 → 폐쇄망 윈도우 검증 → 리눅스 운영)** — 덤프 폴더는 BSON이라 OS 무관, 세 단계 모두 "폴더 놓고 명령 1개":
  1. 맥(개발): `npm run reg:ingest -- --file <개정.hwp>` → `bash scripts/export-rag-db.sh` → `rag-update-YYYYMMDD/` USB 반입
  2. 윈도우(작동테스트): 폴더를 `data\mongo-snapshot\`에 복사 → `update-rag-db.ps1 -Tools <bin>` → 패널 확인
  3. 리눅스(운영): 같은 폴더를 서버 리포 `data/mongo-snapshot/`에 복사 → `bash scripts/update-rag-db.sh`(최신 폴더 자동 선택) → sagyu:build + 캐시 새로고침
> `mongodump`는 `--collection`을 **1개만** 받는다(다중 지정 시 마지막만 적용) — 스크립트가 컬렉션별 3회 호출로 처리하니 수동 덤프 시 주의.
