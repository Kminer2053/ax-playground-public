# 사규 지식그래프 — 관계 스키마 & 추출 표준

> **목적**: 그래프 빌드(클라우드 Opus 일괄)와 **증분 수정(폐쇄망 gemma 단독)** 이 **동일 규격**을 따르게 하여, 시간이 지나 규정이 하나씩 추가돼도 그래프 품질이 유지되도록 한다.
>
> **설계 원칙 한 줄**: *지능을 로컬모델에 두지 말 것.* 유형 판정은 **규칙**으로, 판단 기준은 **Opus 예시**로, 근거문장은 **템플릿**으로, 어려운 건 **사람(검토 큐)** 으로 — 로컬모델의 일은 작고 경계 짓는다.
>
> **상태**: 초안 v0.1 (2026-06-28). Opus 재생성 작업에서 얻는 노하우를 §8에 계속 반영하는 **리빙 도큐먼트**.

관련: [RAG_GRAPHRAG.md](RAG_GRAPHRAG.md) · 구현: `src/lib/regulations-graph-build.ts`(추출·검증·증분) · `src/lib/regulations-graph.ts`(런타임 확장) · 평가: [[rag-benchmark]]

## 1. 엣지 종류(kind)

| kind | 정의 | 대상 | 비고 |
|---|---|---|---|
| `ref` | 내부 규정 간 상호참조(조문→조문/문서) | 내부 문서·조문 | 아래 **관계유형(rt)** 으로 세분 |
| `law` | 외부 법령(국가계약법·시행령·예규 등) 포인터 | 외부(코퍼스 밖) | 확장 대상 아님. **rt 타이핑 권장**(§3 확장) |
| `hier` | 문서 상하위 위계(규정>세칙>지침>편람>매뉴얼>계약서) | 내부 문서 | 사용자 확정(xlsx) 기반, 자동추출 아님 |

**엣지 필드(ref 기준, `regulations-graph-build.ts`):**
```
{ kind:"ref", sdoc, sci, sname, rt, tt:"doc"|"chunk", tdoc, tci?, tname?, conf, reason, srcHash }
```
- `sdoc/sci/sname` = 출처 문서/청크index/조문명 (참조를 **하는** 쪽)
- `rt` = 관계유형(§2·§3) · `tt/tdoc/tci/tname` = 대상(참조 **되는** 쪽)
- `rtConf` = 신뢰도(상/중/하) — §5 게이팅용. (구판 표기 `conf`는 오기 — DB 실필드는 `rtConf`(재타이핑 스크립트 산출, 2,622건), `conf`는 0건. 증분 빌더 `updateGraphForDoc`는 현재 신뢰도 미기록)
- `reason` = 관계 근거문장 — **템플릿으로 채움**(§4). 현재 비어 있음 → 표준화 대상
- `srcHash` = 출처 조문 본문 해시(sha1 24자) — **재적재 증분 갱신 키**(2026-07): 해시가 같으면 그 조문의 엣지를 재도출 없이 인덱스만 재매핑해 재사용(Opus 품질 보존·LLM 비용=변경분만). `rag_vectors.h`도 동일 해시.
- 보조 kind `arthash`(문서당 1건): `{ kind:"arthash", sdoc, hashes[] }` — **엣지 0개 조문**의 해시 박제(무변경이면 재도출 skip — 재적재마다 gemma가 재도출해 그래프가 점증 드리프트하던 문제 방지).

**방향 규약(중요)**: 엣지는 항상 **`출처(인용하는 조문) → 대상(인용되는 규정)`**. `rt`는 "출처가 대상을 어떻게 참조하는가". 로컬모델 방향 흔들림을 막기 위해 **방향은 규칙으로 고정**(트리거가 있는 조문이 항상 source).

## 2. 관계유형(rt) — 현행 7종 (gemma 분류 중)

각 유형 = **정의 + 트리거 어구(규칙 우선) + 방향 + 예시**. 트리거로 잡히면 규칙 확정, 모호할 때만 LLM.

| rt | 정의 | 트리거 어구(규칙) | 예시(source → target) |
|---|---|---|---|
| **근거** | 출처가 대상을 법적 근거로 삼음 | `…에 따라` · `…에 근거하여` · `…의 규정에 의하여` · `…에서 정하는 바에 따라` | 「급여 규정」 제20조 → 제18조(퇴직금) |
| **서식첨부** | 출처가 대상의 별표/별지 서식을 사용 | `별지 제N호 서식` · `별표 제N호` · `…서식에 따른다` · `별표와 같다` | 「급여 규정」 제21조 → 별표 제4호 |
| **준용적용** | 출처가 대상을 준용·적용 | `…을 준용한다` · `…를 적용한다` · `…의 예에 따른다` | 「상업시설 계약서」 제26조 → 「철도구내영업 규정」 |
| **절차** | 출처가 대상에 정한 처리 절차·방법을 따름 | `…의 절차에 따라` · `…에서 정한 절차` · `처리절차는 …` | 「인사 규정」 제12조 → 제24조(파견근무) |
| **위임** | 출처가 세부사항을 대상에 위임 | `세부사항은 …에서 정한다` · `…에 위임한다` · `…이 따로 정한다` | 「위임전결규정」 제5조 → 「감사규정」 |
| **정의** | 출처가 대상의 용어 정의를 원용 | `…의 정의는` · `용어의 정의` · `…에서 정의한 바와 같다` | 「급여 규정」 제4조 → 제10조 |
| **예외** | 출처가 대상의 예외·단서를 참조 | `다만, …는 제외` · `…는 그러하지 아니하다` · `예외로 한다` | 「급여 규정」 제27조(비상시) → 제26조(지급일) |

> 화이트리스트 `RT_SET`(코드)에 일치하지 않는 출력은 `기타`로 폴백 후 **검토 큐**로.

## 3. 관계유형 — 확장 후보 (Opus 재생성 시 도입, 벤치마크 검증 후 채택)

답변 생성에 실제 쓰이고 추출 신뢰도가 받쳐주는 것만. *유형만 늘리고 안 쓰면 무의미*(그래프 교훈).

| rt(확장) | 정의 | 트리거 어구 | 답하게 되는 질문 | 추출난이도 |
|---|---|---|---|---|
| **상충·우선** | 충돌 시 우선/배제 관계 | `…에 우선하여 적용` · `…와 상충하는 경우` · `다른 규정에도 불구하고` · `…이 우선한다` | "X와 Y 충돌 시?" | 중 |
| **개정·대체·폐지** | 출처 시행으로 대상을 대체/폐지(버전·효력) | (부칙) `종전의 …는 폐지` · `…를 …로 본다` · `…를 대체한다` | "언제부터 효력? 구버전?" | 중 |
| **법령 위임근거** | 내부규정이 외부법령 위임/시행에 근거(`law` 엣지 타이핑) | `○○법 제N조의 위임에 따라` · `○○법 시행을 위하여` | "이 내부기준은 무슨 법 근거?" | 상(Opus 강점) |
| **제재·벌칙 연계** | 의무 위반 → 징계/제재/변상 규정 연결 | `위반 시 …에 따라 징계` · `…한 자는 …에 따라 변상/처벌` | "위반하면 어떻게 되나?" | 중 |
| **선후·전제** | 절차 순서/전제조건(generic 절차보다 구체) | `…를 거친 후` · `사전에 …하여야` · `…완료한 경우에 한하여` | "…하려면 무슨 단계?" | 중상 |
| **특례** | 일반규정에 대한 특례(generic 예외와 구분) | `…에 대하여는 특례를 둔다` · `…의 경우 특례로` | 특정 대상 특례 | 중 |
| ~~유사·대비~~ | A와 B의 이동(異同) | (본문에 명시 안 됨) | "X vs Y 차이?" | **하 — 보류**(환각 위험) |

## 4. 근거문장(reason) — 자유생성 금지, 템플릿 채우기

로컬모델 자유생성은 환각 → **트리거 매칭 결과로 템플릿을 채운다**. (Opus급 생성 없이 문장 품질 안정)

| rt | 템플릿 |
|---|---|
| 근거 | `「{sdoc}」 {sname}은(는) 「{tdoc}」 {tname}을(를) 근거로 한다` |
| 준용적용 | `「{sdoc}」 {sname}은(는) 「{tdoc}」 {tname}을(를) 준용한다` |
| 서식첨부 | `「{sdoc}」 {sname}은(는) 「{tdoc}」 {tname} 서식을 사용한다` |
| 위임 | `「{sdoc}」 {sname}은(는) 세부사항을 「{tdoc}」에 위임한다` |
| 상충·우선 | `「{sdoc}」 {sname}은(는) 「{tdoc}」에 우선하여 적용된다` |
| 법령 위임근거 | `「{sdoc}」 {sname}은(는) {tdoc}(외부법령)의 위임에 근거한다` |
| (그 외) | `「{sdoc}」 {sname} ─{rt}→ 「{tdoc}」 {tname}` |

> 런타임 관계배선(`【규정 간 관계】`)은 이 `reason`을 그대로 노출 → 답변의 관계 서술이 풍부해짐.

## 5. 추출 파이프라인 표준 (Opus·gemma 공통 3단계)

```
① 규칙 후보·유형 추출 (결정론, LLM 불필요)
     extractCandidatesForDoc: 정규식으로 참조 후보 + 트리거로 rt 1차 판정 + 방향 고정
        ↓
② 검증 (LLM)  — gemma(증분) / Opus(일괄)
     - is_real? (실제 상호참조 vs 외부법령 오인·단순언급)
     - 규칙으로 rt 못 정한 모호분만 유형 판정
     - few-shot: 시드 그래프(Opus 라벨)에서 유사 예시 K개 주입 → Opus 기준에 정박
     - 출력 형식 고정: "번호:Y|N:유형:신뢰(상/중/하)"   (reason은 ④에서 템플릿)
        ↓
③ 신뢰도 게이트
     - 규칙 트리거 명확 & LLM Y & 신뢰 상  → 자동 반영
     - 모호(규칙 약함 | 신뢰 중·하 | RT_SET 불일치)  → 검토 큐(§6)
     - LLM N  → 폐기 (외부법령이면 law 포인터로)
        ↓
④ reason 템플릿 채움(§4) → 저장
```

**역할 분담**
- **규칙(①)**: 드리프트 0. 비중을 최대화 — 유형 대부분을 여기서 확정.
- **gemma(②)**: is_real + 모호 유형만. few-shot으로 정박. **새 문서의 outgoing 엣지**(자기 문서 텍스트 보유분)에 집중.
- **사람(③ 검토 큐)**: 저신뢰·상충탐지 등 어려운 것만.
- **Opus(②, 일괄)**: 최초 빌드 + **주기적 재감사**(§7). 그 출력이 gemma의 few-shot 예시은행.

## 6. 검토 큐 흐름 (관리자)

증분(`updateGraphForDoc`)이 만든 저신뢰 엣지는 자동반영하지 않고 **관리자 검토 대기**:

1. 관리자 사규 적재(신규=직상위 입력 / 변경) → 증분 추출·검증
2. 고신뢰 엣지 자동 반영, **저신뢰 엣지는 "관계 검토" 목록**에 (source·target·rt·근거문장·신뢰 표시)
3. 관리자: **승인 / 유형수정 / 기각** (기존 사규적재 UI에 탭 1개 추가)
4. 승인분 반영 → 시드 예시은행에도 추가(다음 증분 few-shot 강화)

## 7. 드리프트 방지 & 재감사 사이클

- **표준 일치**: Opus 일괄빌드와 gemma 증분이 **이 문서의 동일 규칙표·형식·템플릿**을 사용(프롬프트가 같은 §2·§3·§4를 참조).
- **주기적 Opus 재감사**: 폐쇄망에 누적된 gemma 엣지를 모아 (신규문서만 외부 반출 또는 클라우드 접근 시점) **Opus가 일괄 재검토·교정** → 재반입. 분기/반기 사이클.
- **기대 품질**: 규칙+예시+템플릿+검토에 의존 시 증분이 Opus 일괄의 **80~90%** 유지(100%는 비현실적). 자유추론 의존도가 높을수록 하락.

## 8. 노하우 (Opus 재생성에서 학습 → 계속 반영) — 리빙 섹션

### 8.1 Phase1a — 교차규정 엣지 34표본 Opus 재분류 vs gemma (2026-06-28)

**구조 발견(중요)**: ref 엣지 1,809개 중 **런타임 확장이 실제 쓰는 교차규정(tt:doc, 내부대상)은 478개뿐**. 나머지 1,331은 문서 내 조문 간(확장 미사용). 교차규정 rt 분포: **근거 224·준용적용 166·위임 53·정의 25·절차 5·예외 4·서식첨부 1** → 서식첨부/정의/절차/예외는 거의 문서 내. **즉 관계형 확장의 핵심은 근거·준용·위임(82%).**

**gemma 분류 정확도 ≈ 74%**(34표본 중 ~9건 오분류). 신뢰 유형: **위임·근거·정의는 정확**(트리거 명확). 오분류는 아래 패턴:

| 패턴 | 사례 | gemma | 올바른 분류 | 규칙 보강 |
|---|---|---|---|---|
| **준용적용 과용** | "직제규정 제6조에 **의하여**", "…**위반** 시 경고" | 준용적용 | **근거** / 제재연계 | 준용적용은 `준용한다`·`예에 따른다`·`정하지 않은 사항은 …기준` 에만. `…에 따라/의하여`는 **근거** |
| **상충·우선 누락** | "급여규정 제8조**에도 불구하고**…", "자산관리규정**에도 불구하고** 적용" | 준용적용/예외 | **상충·우선(신규)** | `…에도 불구하고 …적용/한다` → 상충·우선. **즉시 채택** |
| **예외 vs 한정 혼동** | "취업규칙 제56조에 **해당하는 직원에 한한다**" | 예외 | **근거(조건)** | `…는 제외`=예외 / `…에 한한다·한정`=근거(조건). 구분 |
| **부칙 잡음** | 위임전결규정 부칙→직제규정 | 준용적용 | 개정·시행(신규) | 부칙 청크는 추출 제외 또는 **개정·시행**으로 |

**검증된 확장유형 우선순위**: ① **상충·우선**(트리거 `…에도 불구하고` 명확, 2건 즉시 발견) ② 개정·시행(부칙) ③ 제재·벌칙 연계(`위반 시 …`).

**기타 노하우**
- **다중관계 엣지 존재**: 「전문직사원 운용세칙」 제6조 → 채용시행세칙은 절차+서식첨부 동시. 현재 단일 rt라 주관계 택1 → 추후 보조관계 허용 검토.
- **절차 vs 근거 경계 모호**("…에 따라 조치/처리"): 저위험(둘 다 "타 규정에 의존"). 주관계만 맞으면 OK.
- **방향**: 표본 전부 출처(트리거 보유 조문)→대상 방향 정확. 방향 규칙 고정(§1) 유효.

### 8.2 Phase1b — 결정론 규칙 분류기 478엣지 적용 (2026-06-29)

`regulations-rel-classify.ts`(§2·§3 규칙 코드화)를 교차규정 478엣지에 적용, gemma와 대조.

**중요 정정 — 규칙 단독은 brittle**(앞선 "규칙만으로 74→90%"는 과낙관):
- **chunk 전체 매칭 → 오발**: 조문에 우연히 있는 "별표"로 근거→서식첨부 **98건 오발**. → **절(sentence) 국소화**(대상이 든 절만)로 14건까지↓. (노하우: 규칙은 반드시 **대상-국소화**)
- **그래도 어구 변이를 못 따라감**: 위임을 "정하는 **바에** 따른"으로 잡으면 "정하는 **지급기준에**/**것에** 따른"을 놓쳐 위임→근거 오변환. 정규식으로 위임/근거/정의 변이를 다 못 가림 + 한 조문 다절(多節) 귀속 한계.
- **신뢰도 분포: 상 71(18%, 신뢰) / 중·하 407(82%, LLM 필요)**.

**검증된 것**: 신규유형 규칙은 **고정밀**. `…에도 불구하고`→상충·우선, `위반+제재`→제재·벌칙은 gemma가 놓친 걸 정확히 발굴(준용/예외로 오분류돼 있던 것). 준용적용 과용도 규칙이 명확히 식별.

**표준 갱신(§5 정책 확정)**:
> 규칙층 = **고정밀·저재현**. conf=상(명시적 준용/위임/상충·우선/제재)만 **자동 채택**. conf=중·하(근거/위임/정의 모호 다수)는 **LLM(few-shot + 절-국소화 컨텍스트)** 으로 최종 타이핑 + 검토 큐. *"규칙만"이 아니라 "규칙(명확·신규) + LLM(모호 다수) 하이브리드 + 신뢰도 게이트"* 가 로컬 증분 품질을 유지하는 현실적 답.

→ 전면 재타이핑은 brittle 규칙 일괄쓰기 금지. **Phase2 Opus**가 절-국소화 컨텍스트로 모호분을 타이핑하고, 그 출력이 gemma few-shot 예시은행이 된다.

### 8.3 Phase2-B — Opus 모호엣지 30개 재타이핑 (2026-06-29)

규칙 저신뢰(conf 중·하) 교차규정 엣지 30개를 Opus가 절-국소화 컨텍스트로 재타이핑. **핵심: gemma·규칙 단독 모두 부족하고 상보적 — Opus가 조정한다.**

| 구도 | 사례 | 시사점 |
|---|---|---|
| **규칙○ gemma✗** | 준용→근거(#3,5)·예외→상충·우선(#26)·예외→한정/근거(#28,29) | 규칙이 gemma의 준용 과용·예외 오용을 교정 |
| **gemma○ 규칙✗** | 위임(#6~10: "정하는 것에/지급기준에/으로 정한다")·정의(#23,25: 정의문 내 "에 따라")·예외(#27) | 규칙은 어구변이·정의문 맥락에 약함 → LLM 필요 |
| **둘 다 놓침** | 위반→**제재·벌칙**(#1,2)·부칙→**개정·시행**(#4) | 신규유형은 Opus라야 잡음 |

**확정 규칙(few-shot에 반영, `data/graph/fewshot-rel.json` 17개)**:
- 위임 변이: "정하는 {바/것/기준/사항}에 따라", "…으로 정한다", "…이 정하는" → **위임**(‘에 따라’만 보고 근거 오판 금지)
- 정의문 내부의 "…에 따라/에 의해"는 **정의**(‘…란/이라 함은 … 말한다’ 문형이면 정의)
- "…에 해당하는 자에 **한한다**"=한정→**근거** / "…는 **제외**"=**예외** (구분)
- "…에도 불구하고 … 적용"→**상충·우선** / "위반…(경고·징계·제재)"→**제재·벌칙**

→ 이 few-shot으로 gemma 증분도 같은 판정 가능(Opus 부재 시). **이것이 "로컬모델 단독 품질유지"의 실체.**

### 8.4 Phase2-C — gemma+few-shot 전수 재타이핑: **역효과(롤백)** (2026-06-29)

생산 경로(폐쇄망 = gemma) 검증을 위해 gemma+few-shot(B 예시은행)으로 478 전수 재타이핑.

**결과: 더 나빠짐 → 롤백.** Opus 골드(B-30) 대비:
| | 정확도(골드 대비) |
|---|---|
| gemma 단독 | **60%** |
| gemma + few-shot | **53%** (↓) |
| Opus | 100%(기준) |

**원인**: 소형 로컬모델(gemma-4-e2b)은 few-shot에 **과민** — 예시은행에 위임 사례가 많자 **위임으로 과일반화**(근거·준용·절차·정의를 위임/준용으로 대량 오변환, 위임 53→114). naive "예시 투입"이 오히려 분포를 망침. DB는 rt_old로 전량 롤백(검증된 원본 유지).

**→ 사용자 질문("로컬 단독 품질유지")에 대한 최종·정직한 답:**
1. **naive few-shot은 위험** — 균형·보정 없이는 소형모델을 악화시킴.
2. **현실적 로컬 레시피**: 고정밀 규칙(상충·우선·제재·명시 트리거, conf상 자동) + **gemma 단독**(60~74%, few-shot보다 나음) + 저신뢰 사람 검토. → 대략 **60~74% 품질**.
3. **Opus급(gold)은 클라우드에서만** — gemma는 few-shot으로도 Opus를 못 따라감. 폐쇄망은 *주기적 Opus 재감사(배치 반출)* 로 gold를 유지하고, 그 사이 gemma는 위 레시피로 "준수 가능한" 품질을 낸다.
4. 안전한 단발 개선 여지: Phase1b 규칙의 **상충·우선/제재 conf상**(약 15~20엣지)은 신뢰 가능 → 원하면 그것만 선별 반영 가능(현재 미반영).

**결론**: "로컬 단독으로 Opus급"은 비현실적. 표준의 가치는 *규칙층 + 검토 흐름 + Opus 재감사 사이클*에 있고, few-shot은 신중히 균형 잡아야 한다. 측정이 naive few-shot 역효과를 잡아냄.
